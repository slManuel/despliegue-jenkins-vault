# Operación desde una estación con acceso privado a la VPC

Estado actual: código preparado; instalación no ejecutada. AWS bloquea EC2 y Fleet Requests. Ambos EKS tienen API privada. Tener acceso a la consola web no permite ejecutar kubectl contra esas APIs. El usuario decidió diferir la solución de acceso; no se crea EC2 administrativa ni API pública.

## Requisitos y orden

1. AWS debe resolver el caso 179161319400637. Recuperar y verificar el estado Terraform existente de herramientas; no volver a ejecutar bootstrap con estado vacío. Habilitar `AWS_DEPLOY_ENABLED=true` únicamente cuando se autorice reanudar los despliegues. La política del bootstrap que permite una regla de entrada al API del micro está preparada pero pendiente de aplicar con su estado existente.
2. Disponer de una estación/runner con ruta y DNS hacia la VPC, AWS CLI, kubectl, openssl, jq y acceso EKS administrativo autorizado. No se instala software en el equipo del usuario por este procedimiento. Crear contextos `tools` y `development` con `aws eks update-kubeconfig --region us-east-1 --name prueba-devops-jenkins-vault --alias tools` y el equivalente para `prueba-devops-microservicio --alias development`. Verificar nombres, endpoints privados y nodos Ready antes de aplicar.
3. Ejecutar manualmente el workflow de imágenes con `publish_images=true`. Confirmar que ambos paquetes GHCR siguen privados y conceder lectura al repositorio del micro. Los tags son el SHA completo del commit; preferir digest en `CONTROLLER_IMAGE` y parámetro Jenkins `AGENT_IMAGE`. No hay despliegue en el workflow.
4. En tools, aplicar namespaces. Ejecutar `sh scripts/tls.sh`: genera una CA privada y certificado de servidor con SAN `vault.vault.svc.cluster.local`. Claves quedan en `local/`, ignorado por Git, permisos 0600. Custodiar fuera del repo la CA y rotar certificado antes de 90 días. Crear Secret `vault-tls` en vault con `tls.crt`, `tls.key`, `ca.crt` usando `kubectl create secret generic --from-file` y archivos; crear ConfigMap `vault-ca` en jenkins con **sólo** `ca.crt`.
5. Crear en jenkins Secret `jenkins-admin` con claves `username` y `password` desde archivos 0600; Secret `ghcr-pull` con `.dockerconfigjson` desde archivo de credenciales de sólo lectura de paquetes. No usar contraseñas/tokens en comandos, capturas, historial, logs ni Git. Ejecutar `INSTALL_ENABLED=true CONTROLLER_IMAGE=ghcr.io/slmanuel/jenkins-controller:<SHA> sh scripts/install-tools.sh`.
6. Inicializar Vault **interactivamente** (`kubectl -n vault exec -it vault-0 -- vault operator init`). Guardar claves de unseal separadas y root token fuera del repo/logs. `vault operator unseal` solicita cada clave interactivamente; nunca pasarlas como argumentos. Es un solo nodo Raft, sin HA ni auto-unseal: cada reinicio requiere intervención. Backup cifrado de Raft y restauración deben verificarse antes de uso real.
7. Desde una estación con Vault CLI y jq, abrir un túnel privado `kubectl -n vault port-forward svc/vault 8200:8200`; exportar `VAULT_ADDR=https://localhost:8200` y `VAULT_CACERT=<ruta-absoluta>/local/tls/ca.crt`. Autenticarse con `vault login -no-print` (prompt interactivo, token helper). Obtener `TOOLS_ISSUER` y `DEVELOPMENT_ISSUER` con `aws eks describe-cluster --query cluster.identity.oidc.issuer --output text`; son URLs públicas JWKS, no API públicas del clúster. Exportar ambos y ejecutar `sh scripts/configure-vault.sh` desde la raíz del repo. Configura mounts JWT separados, audience vault, subject exacto del SA, TTL máximo 5 min y datos **de demo**. Revocar el token administrativo al finalizar (`vault token revoke -self`). No se necesita token reviewer permanente ni `system:auth-delegator`: Vault valida firmas JWKS del issuer EKS mediante NAT. JWT emitidos pueden seguir válidos hasta su vencimiento aunque se borre el SA.

## Conexión privada entre clústeres y desarrollo

El DNS `vault.vault.svc.cluster.local` sólo funciona dentro de tools. El Service `vault-private` crea un **NLB interno TCP**, sin terminación TLS, con fuentes `10.0.0.0/16`. Obtener su hostname con `kubectl --context tools -n vault get svc vault-private -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'`. Sustituir `REPLACE_VAULT_INTERNAL_DNS` en `devops-java-service/k8s/vault.yaml` por ese hostname. VSO y CSI mantienen `tlsServerName`/`vaultTLSServerName=vault.vault.svc.cluster.local`; el certificado verifica ese SAN aunque el transporte use DNS del NLB. **No desactivar verificación TLS.** Probar desde development `openssl s_client -connect <NLB>:8200 -servername vault.vault.svc.cluster.local -CAfile ca.crt -verify_return_error`; health debe responder sin exponer claves. Verificar target health del NLB y reglas SG; permisos del controlador cloud y conectividad real están pendientes de ejecución.

En development crear namespaces `development` y `csi`, aplicar `k8s/namespace.yaml` y `k8s/identity.yaml` del micro. Copiar **sólo CA pública** como Secret `vault-ca` en development y ConfigMap `vault-ca` en csi. Crear `ghcr-pull` en development. Ejecutar `INSTALL_ENABLED=true sh scripts/install-development.sh`: driver CSI 1.6.1 + provider Vault 1.7.4 + VSO 1.6.0 con manifests oficiales vendorizados; sin Helm. Aplicar `k8s/vault.yaml` del micro ya configurado y esperar `VaultStaticSecret` reconciliado. La compatibilidad de esquemas se valida localmente; la compatibilidad funcional con EKS 1.36/JWT y el montaje real requieren esta prueba integrada.

El driver CSI upstream usa privilegios y hostPath para registrar/montar volúmenes del kubelet. Es una excepción necesaria del componente de nodo, **no** del agente Jenkins. El agente usa BuildKit rootless, sin Docker socket ni `privileged`; necesita seccomp Unconfined y `--oci-worker-no-process-sandbox` en ese contenedor. Ejecutar sólo builds de código confiable en namespace separado, sin multitenencia. VSO requiere RBAC de controlador y provider CSI TokenRequest; conservar manifests y revisarlos al actualizar.

## Jenkins y despliegue

Desde la estación privada, `kubectl --context tools -n jenkins port-forward svc/jenkins 8080:8080`; abrir localhost, login del Secret administrativo. Crear Pipeline from SCM del repo privado `devops-java-service`, rama main, Jenkinsfile raíz, con credencial GitHub de sólo lectura. Instalar credenciales Jenkins: `registry-credentials` (username/PAT GHCR write:packages, mínima lectura del repo necesaria) y `kubeconfig-development` (Secret file).

Para la segunda, emitir un token temporal de SA `jenkins-deployer` **desde development** con `kubectl create token -n development jenkins-deployer --duration=1h`, escribirlo directamente en un archivo privado; construir kubeconfig con endpoint/CA **del clúster micro** y context **development**, sin imprimir token. El RBAC sólo permite actualizar despliegue/secreto en development. Credencial caduca: renovar antes del job; no es identidad permanente de producción. No almacenar en repositorio ni artifact. El SG de API micro permite TCP443 desde SG de nodos tools mediante Terraform. Comprobar `kubectl auth can-i` con la credencial antes del job: puede patch deployment/secret; no listar namespaces ni administrar cluster.

Cambiar el CIDR documental `198.51.100.0/24` de `k8s/service.yaml` por IP/CIDR del evaluador; el NLB de evaluación HTTP sólo devuelve datos de demo. Aplicar Service una vez. Ejecutar pipeline con `AGENT_IMAGE` publicado: JWT proyectado → Vault → test Java con env → build → push digest → Secret env/Deployment → rollout de dos réplicas. `FEATURE_FLAG` viene de VSO y `application.properties` del CSI. El manifiesto inicial no se aplica con `REPLACE_COMMIT`; Jenkins sustituye por digest antes de kubectl apply. Activar `EXPOSE_DEMO_VALUE=true` sólo con dato de demostración y acceso restringido para evaluar `/api/secret`; default redacted. El endpoint `/api/config` devuelve la propiedad demo y feature flag.

Validar readiness/liveness, `kubectl get pods`, `VaultStaticSecret`, `SecretProviderClassPodStatus`, endpoints vía NLB y rollout con imagen deliberadamente inválida de demo. En actualizaciones el rollback restaura especificación Deployment **y** Secret anterior en memoria. En primera instalación fallida no existe versión anterior: job falla y requiere corregir la primera versión; no destruye recursos ni finge rollback. Nunca adjuntar Secret YAML, kubeconfig, estado, root token o logs con valores reales como evidencia.

NLB, EBS, EKS, NAT y nodos generan costes cuando se apliquen. Este cambio no aplica recursos AWS. StorageClass Retain conserva discos al borrar PVC; borrado posterior requiere autorización específica.
